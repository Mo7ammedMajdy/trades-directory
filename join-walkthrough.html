Joining Shops to Trades

A single query touches three tables in trades_db and turns 8 shops into 10 rows, then 2. Here is what each keyword does, in the order the database actually does it.

The query being traced

SELECT  s.name_ar AS shop, t.name_ar AS trade
FROM    shop s
JOIN    shop_trade st ON st.shop_id = s.id
JOIN    trade t      ON t.id = st.trade_id
WHERE   s.commercial_register IS NULL
ORDER BY s.id;

It answers: which informal tradesmen — the ones with no commercial register — are in the directory, and what trade does each work in?

The order you write it is not the order it runs

This is the single fact that makes everything else make sense. SELECT is written first and executed last. The database has to assemble and filter the rows before it can know which columns to hand back.

Step by step

These are numbered in execution order, not the order they appear in the query.

01

FROM shop s

Load the starting table. s is an alias — a nickname, so the rest of the query can say s.id instead of shop.id. It exists purely to keep the query short.

Rows in hand: 8 — every shop.

02

JOIN shop_trade st ON st.shop_id = s.id

For each shop, find every shop_trade row whose shop_id matches that shop's id. Glue the two rows together side by side.

Seven shops match exactly one link row, so they pass through unchanged. الإتقان matches three, so it comes out three times — once per trade it works in. This is the many-to-many being unpacked, and the row count rising is the proof it happened.

Rows in hand: 10 — up from 8.

03

JOIN trade t ON t.id = st.trade_id

A second join, for the same reason. shop and trade have no column pointing at each other — shop_trade is the only path between them, so you cross it in two hops.

Every link row points at exactly one trade, so nothing multiplies here. Each row simply gains the trade's columns.

Rows in hand: 10 — unchanged. Columns: wider.

04

WHERE s.commercial_register IS NULL

Throw away every row that fails the test. Only shops 6 and 7 have no commercial register, and each works in one trade, so eight rows are discarded.

Because WHERE runs after both joins, it can filter on any column from any of the three tables — they are all present by this point.

Rows in hand: 2 — down from 10.

05

SELECT s.name_ar AS shop, t.name_ar AS trade

Finally, pick which columns come back and what to call them. AS renames a column in the output only — nothing in the database changes.

The rename matters here: both tables have a column called name_ar, so without AS you would get two columns with the same heading and no way to tell them apart.

Rows out: 2. Columns out: 2.

Two things that will catch you

Never write = NULL. NULL means "unknown", and comparing anything to an unknown gives an unknown — not true, not false. So WHERE commercial_register = NULL matches nothing at all and raises no error, which is the worst combination. Use IS NULL and IS NOT NULL.

An alias from SELECT cannot be used in WHERE. Given SELECT s.name_ar AS shop, writing WHERE shop = '…' fails with column "shop" does not exist. Look back at the first diagram: WHERE ran before SELECT, so that name had not been invented yet. Repeat the real column instead.
